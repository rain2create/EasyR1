# EasyR1 项目核心概念详解

本文档详细解释 EasyR1 训练流程中的关键架构设计，包括计算模式、资源管理和显存优化策略。

---

## 一、计算模式：分卡计算 vs 统一计算

### 1.1 概念定义

| 计算模式 | 执行位置 | 数据处理方式 | 典型场景 |
|---------|---------|-------------|---------|
| **分卡计算** | Worker 进程（多卡并行） | 数据自动切片，各 Worker 处理 1/N 数据 | 大模型推理/训练 |
| **统一计算** | Driver 进程（单点） | 完整数据在单点计算 | 轻量级统计/分组计算 |

### 1.2 为什么要分卡计算？

**根本原因：单卡显存无法承载大模型**

```
7B 模型显存占用估算：
- 模型权重 (bf16): ~14GB
- 优化器状态 (Adam): ~28GB  
- 梯度: ~14GB
- 激活值: ~10-20GB
- 总计: ~60-80GB > 单卡 24GB/40GB/80GB

解决方案：
┌─────────────┐  ┌─────────────┐      ┌─────────────┐
│   GPU 0     │  │   GPU 1     │ ...  │   GPU 7     │
│  1/8 权重   │  │  1/8 权重   │      │  1/8 权重   │
│  1/8 数据   │  │  1/8 数据   │      │  1/8 数据   │
└─────────────┘  └─────────────┘      └─────────────┘
     ↓                ↓                    ↓
   并行计算        并行计算              并行计算
     └────────────────┴────────────────────┘
                    ↓
              All-Reduce 同步梯度
```

**具体原因**：
1. **显存限制**：单卡放不下完整 7B+ 模型权重
2. **计算加速**：8 卡并行理论提速 8 倍（实际受通信影响）
3. **Batch Size 限制**：单卡处理 512×5=2560 条样本会 OOM，分 8 卡每卡仅 320 条

### 1.3 为什么要统一计算？

**根本原因：某些计算必须看到完整数据才能进行**

| 场景 | 必须统一计算的原因 | 如果分卡的后果 |
|-----|------------------|---------------|
| **序列长度平衡** | 需要全局统计所有样本长度，决定如何分配到各 rank | 各 Worker 只能看到自己的 1/8 数据，无法做全局最优分配 |
| **GRPO 组内标准化** | 同一问题的 n 个回答必须在一起才能算组内 mean/std | 同一问题的回答分散在不同 Worker，无法计算组内统计量 |

**代价**：
- 统一计算在 Driver（通常是 CPU）执行，不能利用 GPU 加速
- 数据需要从 Worker 收集到 Driver，有通信开销
- 因此只适用于**轻量级计算**（统计、索引操作），不适用于模型推理

### 1.4 分卡计算的实现机制

**触发方式**：使用 `@register(dispatch_mode=Dispatch.DP_COMPUTE_PROTO)` 装饰器

```python
# Driver 调用时：
actor_rollout_ref_wg.compute_log_probs(batch)  # batch: 2560条

# Ray 自动完成分卡：
# 1. 切分: [0-319], [320-639], ... [2240-2559]  → 各 Worker 320条
# 2. 并发执行 8 个 Worker
# 3. 收集合并结果
```

**数据流向**：
```
Driver (完整 batch: 2560条)
    ↓ (RPC + 自动切片分发)
┌─────────────────────────────────────────────────────────┐
│  Worker 0    Worker 1    ...    Worker 7               │
│  320条       320条              320条                  │
│    ↓           ↓                  ↓                    │
│  并行计算    并行计算            并行计算               │
│    ↓           ↓                  ↓                    │
│  result_0   result_1           result_7                │
└─────────────────────────────────────────────────────────┘
    ↓ (自动收集合并)
Driver (完整结果: 2560条)
```

### 1.5 各步骤的计算模式分布

| 步骤 | 计算模式 | 选择原因 |
|-----|---------|---------|
| **Step 1** Rollout 生成 | 🌐 分卡计算 | 7B+ 模型单卡 OOM，需 8 卡并行生成 |
| **Step 2** 序列长度平衡 | 🖥️ 统一计算 | 需全局统计所有样本长度，Worker 只能看到 1/8 数据 |
| **Step 3** 计算奖励 | 🌐 分卡计算 | 虽然计算轻量，但数据已在各 Worker，本地计算省通信 |
| **Step 4** 重计算 log probs | 🌐 分卡计算 | Actor 是大模型，单卡 OOM，必须分布式推理 |
| **Step 5** 计算 ref log probs | 🌐 分卡计算 | Ref 也是大模型，同 Step 4 |
| **Step 6** 计算 Value | 🌐 分卡计算 | Critic 是大模型，必须分布式 |
| **Step 7** 后处理/优势计算 | 🖥️ 统一计算 | **GRPO 组内标准化需完整组数据，分卡后同组数据分散在不同 Worker** |
| **Step 8** 更新网络 | 🌐 分卡计算 | 反向传播显存占用大，必须分布式训练 |

### 1.6 为什么 Step 7 必须是统一计算？

GRPO 算法要求**组内标准化**：

```python
# 假设 n=5，3 个问题共 15 个回答
数据 = [q1_a1, q1_a2, q1_a3, q1_a4, q1_a5,  # 问题1的5个回答
        q2_a1, q2_a2, q2_a3, q2_a4, q2_a5,  # 问题2的5个回答
        q3_a1, q3_a2, q3_a3, q3_a4, q3_a5]  # 问题3的5个回答

# GRPO 公式: (r - mean(r_group)) / (std(r_group) + eps)
# 问题1的优势计算需要知道 q1_a1~q1_a5 的奖励
```

**如果分卡计算的问题**：
```
Worker 0 收到: [q1_a1, q1_a2, q2_a1, q2_a2, q3_a1...]  ← 打乱了！
Worker 0 不知道 q1_a3, q1_a4, q1_a5 在哪张卡上
→ 无法计算问题1的组内均值！
```

**解决方案**：在 Driver 上统一计算，Driver 能看到完整的 2560 条数据，可以按 uid 正确分组。

## 二、Micro Batch：分与不分的选择

### 2.1 概念对比

| 维度 | 分 micro batch | 不分 micro batch |
|-----|---------------|-----------------|
| **目的** | 节省单卡显存，避免 OOM | 简化代码逻辑，减少循环开销 |
| **实现** | 单卡内再切小份，循环处理 | 一次性处理单卡全部数据 |
| **开销** | 多次前向传播 | 单次前向传播 |
| **适用场景** | 大模型推理/训练（显存紧张）| 轻量级计算（无神经网络）|

### 2.2 为什么要分 micro batch？

**根本原因：单卡显存无法容纳大 Batch**

```
场景： rollout_batch_size=512, n=5 → 2560 条样本
       8 张卡 → 每卡 320 条

问题：320 条样本同时过 7B 模型：
- 输入: [320, 4096] token
- 激活值: 320 × 4096 × 隐藏层 × 精度 ≈ 几十 GB
- 单卡 40GB 会 OOM！

解决方案 - 分 micro batch：
┌──────────────────────────────────────┐
│ 单卡数据: 320 条                      │
│   ↓ split(micro_batch_size=2)        │
│ 160 个 micro batches，每份 2 条       │
│   ↓                                  │
│ for i in range(160):                 │
│     forward(2条)  →  释放激活值       │
│   ↓                                  │
│ 梯度累积 160 次后统一 backward        │
└──────────────────────────────────────┘

效果：任何时刻显存只存 2 条的激活值，而非 320 条！
```

### 2.3 各阶段是否需要分 micro batch

| 阶段 | 是否需分 micro batch | 原因 |
|-----|-------------------|------|
| **Step 1** Rollout 生成 | **是** | KV Cache 显存占用随序列长度线性增长，单卡存不下 |
| **Step 2** 序列长度平衡 | **否** | Driver 本地执行，纯统计操作，无模型计算 |
| **Step 3** 计算奖励 | **否** | 纯 Python 函数（正则匹配），无神经网络 forward |
| **Step 4** 计算 log probs | **是** | Actor 是大模型，单卡 320 条会 OOM（`dp_actor.py:201` 分 micro batch）|
| **Step 5** 计算 ref log probs | **是** | Ref 也是大模型，同 Step 4 |
| **Step 6** 计算 Value | **是** | Critic 是大模型，必须分 |
| **Step 7** 后处理/优势计算 | **否** | Driver 本地执行，GRPO 组内标准化需完整数据 |
| **Step 8** 更新网络 | **是** | 反向传播显存占用是正向的 2-3 倍，最易 OOM |

**关键理解**：
- **Driver 层面**：log prob 计算和 reward 计算都是**一次性调用整个 batch**（通过 `wg.compute_xxx(batch)`）
- **Worker 内部**：只有 log prob 计算**再分 micro batch**，reward 计算**不再分**

### 2.4 两个 micro batch 参数的区别

```yaml
worker:
  actor:
    micro_batch_size_per_device_for_experience: 2  # 经验池计算用 即推理用
    micro_batch_size_per_device_for_update: 1      # 策略更新用
```

| 参数 | 使用阶段 | 计算内容 | 显存需求 | 典型值 |
|-----|---------|---------|---------|-------|
| `experience` | Step 4/5 | 纯 forward (log prob) | 较小（只需激活值）| 2-8 |
| `update` | Step 8 | forward + backward + 梯度 | 大（需存梯度、优化器状态）| 1-2 |

**为什么 update 要更小？**
```
Forward 显存占用: 激活值
Backward 显存占用: 激活值 + 梯度 + 优化器状态 ≈ 3× Forward

所以 update 的 micro batch 通常比 experience 小 2-4 倍！
```

### 2.5 代码层面的体现

**Worker 内部再分 micro batch（log prob 计算）**：
```python
# dp_actor.py - compute_log_prob
# 输入 data: 320 条（已由 Ray 分卡）
def compute_log_prob(self, data):
    # 再分 micro batch！
    micro_batches = data.split(self.config.micro_batch_size_per_device_for_experience)
    # 320 / 2 = 160 个 micro batches
    
    for micro_batch in micro_batches:
        log_probs = self._forward_micro_batch(micro_batch)  # 每次只算 2 条
        log_probs_lst.append(log_probs)
    
    return torch.concat(log_probs_lst)  # 最后拼回 320 条
```

**Worker 内部不再分（reward 计算）**：
```python
# reward/function.py - compute_reward_batch  
# 输入 data: 320 条（已由 Ray 分卡）
def compute_reward_batch(self, data):
    # 不分 micro batch，一次性处理 320 条！
    for i in range(len(data)):  # 遍历全部 320 条
        response_str = self.tokenizer.decode(...)
        score = self.reward_fn(response_str, ground_truth)  # 纯 Python 计算
    return scores
```

**Driver 层面的一次性调用（不分 micro batch）**：
```python
# ray_trainer.py - Driver 代码
# 以下调用都是一次性传整个 batch，由 Ray 自动分卡，Worker 内部再决定是否分 micro

# Step 4: 计算 log probs - Driver 层面不分
old_log_probs = self.actor_rollout_ref_wg.compute_log_probs(batch)  # 2560条一次性

# Step 3: 计算 reward - Driver 层面不分  
reward_tensor = self.reward_fn.compute_reward.remote(batch)  # 2560条一次性

# Step 1: 生成 - Driver 层面分 mini_batch（由 _make_batch_data 控制）
batch = self._make_batch_data()  # 循环累积到 rollout_batch_size
```

## 三、Worker 与资源池

### 3.1 概念定义

| 概念 | 定义 | 类比 |
|-----|------|-----|
| **资源池 (Resource Pool)** | 定义集群 GPU 资源的规格 | 健身房的管理系统（有 8 台跑步机）|
| **Worker** | 实际占用 GPU 执行计算的 Ray Actor | 来健身的人（占用跑步机）|
| **WorkerGroup** | 管理一组 Worker 的集合 | 一个健身团队 |

### 3.2 资源池配置

```python
# 典型配置
resource_pool_spec = {"global_pool": [8]}
# 含义：1 个节点，8 张 GPU

# 多节点配置
resource_pool_spec = {"pool": [8, 8]}
# 含义：2 个节点，每节点 8 卡，共 16 卡
```

### 3.3 Worker 创建过程

```
配置: process_on_nodes=[8], max_colocate_count=1 代表一个worker一张卡

Step 1: 创建 Placement Group（8 个 GPU slot）
┌─────────────────────────────────────────────┐
│ Placement Group                             │
│  ┌─────┐ ┌─────┐        ┌─────┐            │
│  │GPU 0│ │GPU 1│  ...   │GPU 7│            │
│  └─────┘ └─────┘        └─────┘            │
└─────────────────────────────────────────────┘

Step 2: 循环 8 次创建 Worker
┌─────────┐ ┌─────────┐      ┌─────────┐
│Worker 0 │ │Worker 1 │ ...  │Worker 7 │
│ ├─ GPU 0│ │ ├─ GPU 1│      │ ├─ GPU 7│
│ ├─ Rank 0│ │ ├─ Rank 1│     │ ├─ Rank 7│
└─────────┘ └─────────┘      └─────────┘
```

### 3.4 关键参数说明

| 参数 | 含义 | 影响 |
|-----|------|-----|
| `process_on_nodes` | 每节点进程数 | Worker 总数 = 数字之和 |
| `max_colocate_count` | 每 Worker 占几张卡 | 默认 1，即 1 Worker = 1 GPU |
| `use_gpu` | 是否用 GPU | 否的话用 CPU（调试）|

### 3.5 为什么需要资源池？

**场景 1：多角色共享资源**
```python
# 所有角色共享同一个 8 卡资源池
mapping = {
    Role.ActorRolloutRef: "global_pool",
    Role.Critic: "global_pool",  # 共用 8 个 Worker
}
```

**场景 2：多节点训练**
```python
resource_pool_spec = {
    "pool_node0": [8],  # 机器 0
    "pool_node1": [8],  # 机器 1
}
# Worker 0-7 在机器 0，Worker 8-15 在机器 1
```

## 四、三合一架构：ActorRolloutRef

### 4.1 传统分离式架构

```
┌─────────────┐  ┌─────────────┐  ┌─────────────┐
│   Actor     │  │   Rollout   │  │     Ref     │
│  (7B模型)   │  │   (7B模型)  │  │   (7B模型)  │
│  ~14GB      │  │   ~14GB     │  │   ~14GB     │
└─────────────┘  └─────────────┘  └─────────────┘
       ↓                ↓                ↓
   8个Worker       8个Worker        8个Worker
   
共 24 个 Ray Actor 进程，进程开销大
```

### 4.2 三合一架构

```
┌─────────────────────────────────────────────────┐
│           ActorRolloutRef Worker                 │
│                                                  │
│   一个 Worker 进程内具备三种能力：                │
│   ├─ 作为 Actor：计算 log_prob、更新参数         │
│   ├─ 作为 Rollout：vLLM 生成回答                 │
│   └─ 作为 Ref：计算参考模型的 log_prob           │
└─────────────────────────────────────────────────┘
         ↓
    8 个这样的 Worker
    共 8 个 Ray Actor 进程
```

### 4.3 三合一的真正好处

| 优势 | 说明 | 节省什么 |
|-----|------|---------|
| **减少进程数** | 8 个 vs 24 个 Worker | Python 运行时、CUDA Context、通信缓冲区 |
| **显存复用** | 通过 Weight Offload 分时使用 | 同一时间 GPU 上只有 1-2 份权重 |
| **减少通信** | 无需跨进程 RPC 传递中间结果 | 延迟降低 |

### 4.4 权重数量真相

**全参数模式（无 LoRA）**：

| 组件 | 权重状态 | 显存策略 |
|-----|---------|---------|
| Actor | 可训练 | GPU/CPU 动态切换 |
| Ref | 冻结，独立创建 | GPU/CPU 动态切换 |
| Rollout | vLLM 加载，与 Actor 同步 | 生成时活跃，其他时释放 |

**物理上仍是 3 份权重**，但通过 **时间复用 (Temporal Multiplexing)** 节省显存：

```
时间线：
T1: Rollout 生成 → GPU: [Rollout活跃, Actor/Ref在CPU]
T2: Actor 计算   → GPU: [Actor活跃, Ref在CPU, Rollout释放]  
T3: Ref 计算     → GPU: [Ref活跃, Actor在CPU]

同一时间 GPU 上只有 1 份！
```

### 4.5 LoRA 模式（真正的权重共享）

```python
if self._is_lora:
    # LoRA 模式下，Ref 直接引用 Actor 的模块
    self.ref_fsdp_module = self.fsdp_module
```

| 组件 | 权重构成 | 是否共享 Base |
|-----|---------|--------------|
| Actor | Base (冻结) + LoRA Adapter (可训练) | - |
| Ref | Base (冻结) + 禁用 LoRA | ✅ 与 Actor 共享 Base |
| Rollout | 通过 ShardingManager 复用 Actor | ✅ 动态同步 |

**显存占用**：只有 1 份 Base + LoRA Adapter（最省显存）

### 4.6 三合一 vs 传统：对比总结

| 对比项 | 传统分离式 | 三合一 (EasyR1) |
|-------|-----------|----------------|
| Worker 进程数 | 24 个 | 8 个 |
| 权重份数（全参数） | 3 份 | 3 份（时间复用）|
| 权重份数（LoRA） | 3 份 | ~1 份（共享 Base）|
| 进程内存开销 | 高 | 低 |
| 跨进程通信 | 多 | 少 |
| 适用场景 | 超大规模模型 | 7B~70B 主流场景 |

## 六、常见问题 FAQ

**Q1: 为什么 reward 计算不分 micro batch？**
> 两个原因：
> 1. **计算特性**：Reward 是纯 Python 函数（字符串解析、正则匹配），没有神经网络 forward，显存占用极小
> 2. **实现方式**：Reward 在 Worker 收到数据后一次性遍历处理（`for i in range(len(data))`），不需要像模型推理那样切分
>
> 对比：log prob 计算需要过 7B 模型，激活值占显存巨大，必须分 micro batch

**Q2: 全参数模式下三合一真的能省显存吗？**
> **权重数量上**：全参数模式下仍是 3 份权重（Actor/Ref/Rollout），省的不是这个
> **真正节省**：
> 1. **进程开销**：8 个 vs 24 个 Ray Actor，节省 Python 运行时和 CUDA Context
> 2. **时间复用**：通过 Weight Offload，同一时间 GPU 上只有 1-2 份权重（而非 3 份同时）
> 3. **通信减少**：无需跨进程 RPC，延迟更低
>
> **LoRA 模式下**：才真正共享 Base 权重，物理上只有 1 份 Base + LoRA Adapter

**Q3: 为什么 Step 7 优势计算不能分卡？**
> GRPO 算法要求按问题分组（每组 n 个回答），计算组内均值方差（`(r - mean) / std`）
> 
> 如果分卡，同一问题的 n 个回答可能分散在不同 Worker（如 Worker 0 有 q1_a1,q1_a2，Worker 1 有 q1_a3,q1_a4,q1_a5），单个 Worker 无法计算完整的组内统计量

**Q4: 分卡计算和分 micro batch 有什么区别？**
> | 维度 | 分卡计算 (DP) | 分 micro batch |
> |-----|--------------|---------------|
> | **目的** | 解决"模型太大单卡放不下" | 解决"batch 太大单卡 OOM" |
> | **切分维度** | 数据按样本切分（2560条 ÷ 8卡）| 单卡数据再切小份（320条 ÷ 160次）|
> | **执行者** | Ray 自动分发 | Worker 内部代码控制 |
> | **并行度** | 8 Worker 同时执行 | 单卡内串行循环 |
> | **显存效果** | 每卡存 1/8 模型权重 | 每时刻只存 micro_batch 条数据的激活值 |
>
> **关系**：分卡是"横向"扩展（多卡并行），分 micro batch 是"纵向"切片（单卡内串行）

**Q5: max_colocate_count > 1 会怎样？**
> 一个 Worker 占多张 GPU（张量并行 TP），用于超大模型（如 70B+）单卡放不下时。EasyR1 默认用 FSDP (max_colocate_count=1)，即 1 Worker = 1 GPU。
